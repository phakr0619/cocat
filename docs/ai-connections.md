# AI のつなぎ方（設計）

Cocat を自分の組織で立てる人が、AI の機能を少ない手間でつなげるようにする。会社ごとに要る値を Cocat の側で確かめておき、立てる人はその値を入れるだけで使えるようにする。

状態: 設計中（2026-11-15）。作る前に PR で話す。

## 1. 目的と、やらないこと

**目的**

- AI の会社ごとに、要る値と、その値をどこで見るかを、確かめた結果として一覧にする
- 試すときは、ブラウザで値を入れればすぐ使える（今の形）
- 組織で配るときは、キーを使う人のブラウザに渡さない。キーは AWS の Systems Manager の Parameter Store に置き、サーバー側の中継から AI の会社を呼ぶ
- 使う人の設定を、立てる人が先に決めておける

**やらないこと**

- 利用者のログイン。中継は、サイトと同じ守りの内側に置く前提にする。サイトの守り方（IP の制限・SSO など）は、立てる組織が決める
- AWS 以外で動く中継（今の公開の手順が AWS の S3・CloudFront のため）。秘密を読む部分は差し替えられる形にしておく

## 2. 全体の形

部品は 3 つ。

1. **接続の型の一覧**: 会社ごとの要る値・認証の形・送る形などのデータ（3 章）
2. **キーの置き場所**: ブラウザだけの形と、中継の形（4 章）
3. **組織の設定ファイル**: 立てる人が先に決めておく値（5 章）

```
[試す形]    ブラウザ（キー） ──────────────→ AI の会社
[中継の形]  ブラウザ ──→ CloudFront /api/ai ──→ Lambda ──→ AI の会社
                                                  │
                                                  ├ Parameter Store（AWS の外の会社のキー）
                                                  └ IAM ロール（Bedrock。キーは無い）
```

## 3. 接続の型の一覧

会社ごとに 1 つのデータを持つ。このデータから、設定の画面・資料の表・接続のテストを作る。手で書いた表と画面がずれないようにするため。

| 項目 | 中身 |
| --- | --- |
| 要る値 | 欄の名前・秘密か・例・どこで見るか（ポータルの道順） |
| 認証の形 | `Authorization: Bearer`・`api-key` のヘッダー・`x-goog-api-key`・IAM（中継のみ）など |
| 送る形 | Gemini・OpenAI の Chat Completions・Bedrock の Converse など |
| JSON の答えの縛り方 | 構造化出力・ツールの引数・JSON の形の指定 |
| 画像を送れるか | 送れる・送れない（送れないなら、画像と PDF を読む機能を出さない） |
| ブラウザから直接呼べるか | 確認済み・未確認・不可（不可なら、試す形では使えない） |
| 確かめた日 | 本物で通した日。未確認のものは空 |

最初に入れる会社と、今わかっていることを次に示す。

| 会社 | 要る値 | 認証 | 送る形 | 確かめ |
| --- | --- | --- | --- | --- |
| Gemini（Google AI Studio） | キー、モデル | `x-goog-api-key` | Gemini | 確認済み（今の形） |
| Bedrock | リージョン、モデル（推論プロファイル）、キー（試す形のみ） | 試す形: Bedrock の API キー（Bearer）。中継の形: IAM ロール | Converse | これから確かめる |
| Azure OpenAI | エンドポイントの URL、デプロイの名前、キー | `api-key` | OpenAI の Chat Completions（v1） | 未確認（試す環境が無い） |
| OpenAI と同じ形の口 | ベースの URL、モデル、キー（無くてもよい） | Bearer | OpenAI の Chat Completions | 社内のプロキシ・Ollama などで使う。確かめはその都度 |

M365 Copilot の Chat API は、ライセンス・組織の管理者のアプリ登録・答えの形を縛れるかの条件が多いため、最初は入れない。

### 3.1 接続のテスト

設定の画面に「接続を確かめる」を置き、次の順に確かめる。失敗したら、どの欄を見直すかを出す。

1. 届くか（ブラウザから直接呼ぶときは、CORS で断られないか）
2. キーや権限が正しいか
3. モデル（デプロイ）があるか
4. 決まった形の JSON で答えるか（短い問いを 1 つ送る）
5. 画像を読めるか（小さな画像を 1 枚送る。画像を使わないなら飛ばせる）

4 と 5 は料金がかかる（どちらも 1 回で 1 円に満たない量）。押す前にそう書く。

## 4. キーの置き場所

| | 試す形 | 中継の形 |
| --- | --- | --- |
| キーの置き場所 | 使う人のブラウザ（今の形。既定はメモリだけ） | Parameter Store の SecureString。Bedrock は IAM ロールで、キーは無い |
| ブラウザが呼ぶ先 | AI の会社 | 同じサイトの `/api/ai` |
| 使う人がすること | キーを貼る | 何もしない |
| 向いている使い方 | 試す・個人で使う | 組織で配る |

ブラウザから Parameter Store を直接読む形は取らない。ブラウザに AWS の認証情報を渡すことになり、キーを渡すのと変わらないため。

### 4.1 中継

- 今の OPSIN の Lambda と同じ形にする（Lambda の関数 URL を、CloudFront の OAC を通してだけ呼べるようにする）。サイトと同じ所にあるので、CORS は起きない
- 中継がすること
  - 組織の設定で許したモデルか、送る大きさが上限の内かを確かめる
  - キーを Parameter Store から読む。読んだ値は Lambda の中に数分だけ持つ
  - AI の会社を呼び、答えを返す
- 中継がしないこと: 送った文章や答えの記録。残すのは、時刻・会社・モデル・トークン数・成功か失敗かだけ
- ブラウザの側では、試す形と同じ呼び出しの部品を使い、送り先だけを中継に替える。機能ごとのプロンプトと、答えの形を確かめる処理は、どちらの形でも同じものを使う
- 秘密を読む部分は差し替えられる形にし、後で Secrets Manager を足せるようにする

### 4.2 Terraform

- `infra/` に、中継を作るかどうかの変数を足す。既定は作らない（誰でも開ける公開のサイトでは作らない）
- 作るもの: Lambda、IAM ロール、CloudFront の `/api/ai/*` の振り分け、Parameter Store の箱
- Parameter Store の値は、Terraform では入れない。仮の値で箱だけ作り、値の変更は無視する（`ignore_changes`）。本物のキーは、立てる人がコンソールか CLI で入れる。キーを Terraform の state に残さないため
- IAM ロールに付ける権限は、使う会社に合わせて絞る
  - Parameter Store を使う会社: そのパラメーターだけの `ssm:GetParameter` と、復号の `kms:Decrypt`
  - Bedrock: 許したモデルだけの `bedrock:InvokeModel`

## 5. 組織の設定ファイル

サイトの一番上のフォルダーに `cocat-config.json` を置くと、画面はそれを読んで AI の設定を決める。無ければ今の形（使う人がすべて選ぶ）。

```json
{
  "ai": {
    "mode": "relay",
    "provider": "bedrock",
    "region": "ap-northeast-1",
    "models": ["（使ってよいモデル）"],
    "locked": true
  }
}
```

- `mode`: `browser`（試す形）か `relay`（中継の形）
- 秘密でない値（エンドポイント・デプロイの名前・リージョン・モデル）だけを書く。キーは書かない。書いてあれば、画面は読み込まずに注意を出す
- `locked` が true なら、使う人は会社とモデルを変えられない

## 6. 先に確かめること

1. **時間切れ**: AI の答えには 1〜3 分かかることがある。CloudFront が裏の Lambda を待つ時間は、既定で 30 秒、上げても 60 秒（それ以上は申請が要る）。次のどちらかで、間を空けずに少しずつ返す形にする。本物で確かめる
   - Lambda の答えを少しずつ返す形（レスポンスストリーミング）で、待つ間に空白を送り続け、最後に JSON を送る
   - 「受け付け → 後で取りに行く」形
2. **POST の署名**: CloudFront の OAC を通して Lambda の関数 URL に POST するときは、本文のハッシュ（`x-amz-content-sha256`）をブラウザが付けて送る必要がある。ブラウザの暗号の機能で作れるかを試す
3. **Bedrock のモデルの利用**: Bedrock のモデルによっては、初めて使う前にコンソールで手続きが要る。手順に書くために、本物で確かめる
4. **ブラウザから直接呼べるか**: Bedrock の API キーで、ブラウザから Converse を直接呼べるか（CORS）。断られるなら、Bedrock は中継の形だけにする
